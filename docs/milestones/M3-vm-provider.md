# M3: Scaleway Instances runtime with the Docker executor

Spec: `docs/SPEC.md` D30, D31 and section 6.1.

## Binding rules

1. Provider: the Scaleway provider keeps the exported type `ScalewayJobs` (an alias `Scaleway` is fine) and its constructor; `PROVIDER_NAME` becomes `"scaleway"`; the CLI accepts `scaleway` and `scaleway-jobs`. A pool's `runtime` is `instances` (default) or `jobs`; any other value fails `plan` with a message naming the pool.
2. Shared resources stay single: one project, one dispatch key, one cache key, one bucket, one registry namespace. The dispatch policy grants `ServerlessJobsFullAccess`, `ContainerRegistryReadOnly` and `InstancesFullAccess`; existing policies are repaired as in M2.
3. Instances runtime resources: security group `<name>-vm` (inbound drop, outbound accept, stateful), step id `vm:security-group`. No job definition for `instances` pools; no baked image in M3.
4. Start: `POST /instance/v1/zones/<zone>/servers` (zone `<region>-1` unless the provider section sets `zone`), name `<name>-<tag>-<8 hex>`, `commercial_type` from `pool.instanceTypes` or `["DEV1-M", "PLAY2-NANO"]`, falling back to the next type on out-of-stock or quota errors; image: Scaleway's marketplace Docker image resolved by label (verify the label; fallback `ubuntu_noble` with Docker installed by cloud-init), local root volume, `dynamic_ip_required: true`, `routed_ip_enabled: true`, security group from rule 3, tags `ciburst`, `<name>`, `pool:<tag>`, `job:<label job>`, `ciburst-state:starting`, `ciburst-free:<slots>`. Then set user data `cloud-init` (rule 6) and `poweron`. The returned run id is the server id. `StartRequest.env` carries `CIBURST_VM_SECRET`; the provider computes `ciburst_core::vm::token(secret, server_id)` and never passes the secret to the VM.
5. Tags are the shared state (spec 6.1): `ciburst-state:<state>`, `ciburst-free:<n>`, `ciburst-seen:<unix seconds>`, `ciburst-drain:<unix seconds>` when draining starts. `report` rewrites these tags (keeping all others); `claim` lowers `ciburst-free` by one, not below zero; `capacity` lists the pool's servers in states `starting` and `running` and parses the tags; `created_at` from the server's `creation_date`. `list` returns the servers as `Run` (live while `starting` or `running`). `stop` terminates (`action: terminate`, deletes local volumes, releases the dynamic IP).
6. Cloud-init contract between provider and agent, rendered by the provider:
   - `write_files`: `/etc/ciburst/vm.env`, mode 0600, `KEY=VALUE` lines: `CIBURST_RUN_ID`, `CIBURST_VM_TOKEN`, `CIBURST_DISPATCH_URL`, `CI_SERVER_URL`, `RUNNER_TOKEN`, `CIBURST_POOL`, `CIBURST_SLOTS`, `CIBURST_DEFAULT_IMAGE` (the pool's `image`), `CIBURST_TIMEOUT_S` (the pool's `timeoutS`), and when the cache is on `CACHE_TYPE=s3`, `CACHE_S3_SERVER_ADDRESS`, `CACHE_S3_BUCKET_NAME`, `CACHE_S3_BUCKET_LOCATION`, `CACHE_S3_ACCESS_KEY`, `CACHE_S3_SECRET_KEY`, `CACHE_SHARED=true`.
   - `runcmd`, in order: install `gitlab-runner` from `https://gitlab-runner-downloads.s3.amazonaws.com/v18.11.4/binaries/gitlab-runner-linux-amd64` with a pinned sha256 to `/usr/local/bin/gitlab-runner`; copy the agent binary out of the image `<registry endpoint>/vm-agent:edge` (`docker create`, `docker cp <id>:/ciburst-vm-agent /usr/local/bin/`, `docker rm`); write and start `ciburst-vm-agent.service` (`Restart=on-failure`, `EnvironmentFile=/etc/ciburst/vm.env`).
   - The registry endpoint comes from the provider's registry namespace; the drill config sets `registryPublic: true`.
7. Agent, spec 6.1: `CIBURST_SLOTS` slots, each `gitlab-runner run-single --url $CI_SERVER_URL --token $RUNNER_TOKEN --executor docker --docker-image $CIBURST_DEFAULT_IMAGE --docker-privileged --docker-volumes /cache --max-builds 0 --wait-timeout 0 --config /var/lib/ciburst/slot-<n>/config.toml` plus the cache flags verified in M1 (`docs/RUNBOOK.md`), each in its own config dir so each slot has its own system id. Busy slots: distinct values of the label `com.gitlab.gitlab-runner.job.id` over `docker ps`, every 5 s. Report to `POST $CIBURST_DISPATCH_URL/vm` with headers `X-Ciburst-Run`, `X-Ciburst-Token` and body `VmReport` on every change and every `HEARTBEAT_S`. Drain when idle and `uptime % 3600 >= DRAIN_MINUTE * 60`: report `draining`, keep slots polling for `DRAIN_GRACE_S`, back to `busy` if a slot takes a job, else `SIGQUIT` every slot, wait for all to exit, then `POST /terminate` with the same headers, retried with backoff for 10 minutes. Every OS interaction (clock, uptime, process spawn and signal, `docker ps`, HTTP) behind a trait so the drain protocol is unit-tested with fakes.
8. Dispatcher, spec 6.1: pending job event on a pool whose provider returns `Some` from `capacity`: free = sum of `free` over `idle` and `busy` entries; if free > 0, `claim` the entry with the most free slots and answer `200 {"result":"claimed","pool","runId"}`; else start unless the count of non-`draining` entries reaches `maxRuns` (`200 at_capacity`). Pools with `None` keep the M2 behaviour. `POST /vm` and `POST /terminate`: verify `vm::verify(vm_secret, run, token)`, else `401` without body; `/vm` calls `report(run, body, now)`; `/terminate` calls `stop(run)` and answers `200 {"result":"terminated"}`. A request whose JSON body has `ciburst_sweep` equal to the hook token calls `sweep(now)` and answers `200 {"result":"swept","runs":[...]}`. `Dispatcher` gets a `handle_request(method, path, headers, body, now)` entry; the old `handle` stays for the webhook path. The function passes the request path, which Scaleway Functions provide as the URL path; verify how a cron invocation arrives (method, path, body) and record it.
9. Provisioner: generates `CIBURST_VM_SECRET` like the hook token (rotated with `rotate hook`), passes it in `Secrets.vm_secret` and in `run_env` as `CIBURST_VM_SECRET` for VM pools. Host: secret env `CIBURST_VM_SECRET`; a cron `<name>-sweep` every 30 minutes (`*/30 * * * *`) with args `{"ciburst_sweep": "<hook token>"}`, step id `cron`; planned `update` when its args or schedule differ.
10. Sweep, using the limits in `vm.rs`: terminate servers of this deployment in `ciburst-state:starting` older than `SWEEP_STARTING_S`, in `draining` with `ciburst-drain` older than `SWEEP_DRAINING_S`, with `ciburst-seen` older than `SWEEP_SILENT_S` (or never seen and older than `SWEEP_SILENT_S`), and any older than `SWEEP_MAX_AGE_S`. Never a server that reported within `SWEEP_SILENT_S` unless it is past the maximum age.
11. Simulation test: `crates/core/tests/vm_races.rs` drives the dispatcher with a fake VM provider through the races of spec 6.1 (double claim, pending during drain, boot for a job taken elsewhere, silent VM) and asserts that every pending job is served by some slot within one job duration plus one boot, with an injectable clock.
12. Dependencies with explicit versions in your crate's `Cargo.toml`; `cargo deny check` stays green. No network in tests. Verify every Scaleway endpoint and field against the raw SDK sources (`https://raw.githubusercontent.com/scaleway/scaleway-sdk-go/master/api/<api>/<version>/<api>_sdk.go`), not pkg.go.dev.
13. No em or en dashes; no identifying data; brief docs; comments only for a why.
