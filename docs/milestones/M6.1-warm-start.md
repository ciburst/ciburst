# M6.1: warm start

Go for the spec: owner, 2026-10-25 ("spec the optimization"). Spec D48 and D49. Implementation starts after the M6 drill, whose drill consumer run is the baseline. Base commit: named in each agent prompt.

## Scope

1. Pipeline events start one VM per pipeline that will need one, before its first VM job is pending (D48).
2. Lane jobs leave the slots that the pipeline's VM jobs will need (D48).
3. `ignoreJobs` keeps jobs of other runners from starting VMs (D49).
4. Drill: the demo and the drill consumer with and without `warmStart`.

Terms: a VM pool has runtime `instances` or `hetzner`. A VM job is a job that `pool_for(name, stage)` routes to a VM pool; a lane job with `vmFirst` is not a VM job.

## Rules

R1. Config. Top-level `ignoreJobs`: glob patterns over the job name as in M6 rule R1, each non-empty; default empty. A VM pool may set `warmStart` (bool, default true); on a lane it is a validation error. Routing checks `ignoreJobs` first: a match routes nowhere. The pipeline defaults stay as they are.

R2. Hook. The project hook has `pipeline_events: true` besides `job_events`. `plan` shows `update  gitlab hook in project <id>  (pipeline events)` for a hook without it; `FakeGitlab` stores the flag and delivers pipeline events as GitLab does (`X-Gitlab-Event: Pipeline Hook`, `object_kind: pipeline`, `object_attributes`, `builds` with `id`, `name`, `stage`, `status`, `when`, `manual`).

R3. Pipeline events. The dispatcher checks token and project as for job events, then by `object_attributes.status`:
- `pending` or `running`: the warm step (R4).
- `success`, `failed`, `canceled`, `skipped`: deletes the pipeline's records (R5); answer `200 {"result":"closed","pipeline":<id>}`.
- any other: `200 {"result":"ignored","reason":"status","status":"<status>"}`.

R4. Warm step. Builds count when their `status` is `created`, `pending`, `waiting_for_resource`, `preparing` or `scheduled`, their `when` is not `manual` or `on_failure`, `manual` is false, and the name is neither `ciburst-*` nor in `ignoreJobs`. Each counted build routes with `pool_for(name, stage)`; VM jobs are grouped by pool. Without VM jobs: `200 {"result":"ignored","reason":"no_vm_jobs"}`. When the pipeline's record exists already: `200 {"result":"duplicate","pipeline":<id>}`. Otherwise, per VM pool with VM jobs, after the ledger's 2 s wait:
- `warmStart` false: action `disabled`.
- a claim candidate with a free slot (M4 rule R1), or a ledger intent of the last 30 s: action `capacity`.
- live VMs at `maxRuns`: action `at_capacity`.
- else start one VM with every slot free and write it to the burst ledger as a leader whose `slots` positions are all open, so the next `slots` VM jobs of the window ride on it: action `started` with `runId`.

It writes the record (R5) and answers `200 {"result":"warm","pipeline":<id>,"pools":[{"pool":"vm","action":"started","runId":"<id>","vmJobs":3}]}`; log `info warm pipeline="<id>" project="<id>" pool="vm" action="started" run="<id>" vm_jobs="3"` per pool. A failed start logs `error start_failed` and answers 500, as for job events.

R5. Records, in the cache bucket under `ciburst/intents/_pipelines/<pipeline id>/` (an underscore cannot start a pool tag; the lifecycle rule of `ciburst/intents/` expires leftovers): `vm-jobs.json` holds `{"<pool>": [<job ids>]}` from R4; a VM job's pending event writes the empty object `seen/<job id>` when its pipeline has a record (one HEAD per VM job event). The final status deletes the prefix. Reads and writes use the cache key, like the ledger.

R6. Reservation. A lane job with `vmFirst` claims a VM slot only when the claim candidates of its VM pool have more free slots in total than the reserve of its pipeline: `min(slots of the pool, VM jobs of that pool in vm-jobs.json without a seen marker)`, 0 without a record. Otherwise it starts a lane run as today. Reserves of other pipelines are not counted.

R7. Job events. A job whose name matches `ignoreJobs` answers `200 {"result":"ignored","reason":"ignore_jobs"}` before routing; nothing starts.

R8. `check`. New problems: a job whose effective tags name no pool and that `ignoreJobs` does not match (`runs on other runners (tags <tags>) but ignoreJobs misses it: its pending events start VMs`); a job that `ignoreJobs` matches and whose tags name a pool (`is in ignoreJobs but tagged for pool <tag>: no runner starts for it`). `check --suggest` prints `"ignoreJobs": [<names>]` for the first kind; own `ciburst-*` jobs are never listed.

R9. Docs: README (scheduling in four lines, the warm VM's cost), `AGENTS.md` step 4 (`ignoreJobs` instead of "keep them few"), RUNBOOK (pipeline event answers, records, the reservation, failure modes, M6.1 drill), SPEC sections 5.4 (`ignoreJobs`, `warmStart`), 6.1 (warm step and reservation beside the burst ledger) and 6.3, the milestone table.

## Definition of done

`cargo fmt --check`, `clippy -D warnings`, `cargo test` (Windows and `scripts/test-linux.sh`), `cargo deny`, shellcheck and the bootstrap test green. Fake-based tests: a pipeline event with VM jobs in stage 2 starts one VM and its stage 1 VM jobs ride on it; a repeated `running` event answers `duplicate`; job events in the 30 s window before it make it answer `capacity`; a lane job leaves the reserved slot and a VM job's seen marker frees it; `ignoreJobs` answers `ignore_jobs`. Live, demo: a lane stage of about 60 s before a Docker job queues the Docker job under 10 s with `warmStart` and 60 to 100 s without; the delivery list shows `warm` with `started`. Drill consumer: one pipeline each with `warmStart` true and false after a cold start, wall clock, VMs started, VM-hours, lane seconds and cost recorded in the runbook.
