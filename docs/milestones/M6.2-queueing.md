# M6.2: queue first, spill on spare slots

Go: owner, 2026-10-26 ("It has to be possible to leverage some amount of queueing to reach our goal of using only one (or 2 in case of real needed parallelism) VMs while utilizing the compute we already paid for", then "do it"). Spec D53 and D54. Base commit: named in each agent prompt.

## Findings this milestone answers

The drill consumer's first pipeline on lanes plus warm start (2026-10-26, pipeline 2988692655) used 4 VMs where 1 would do:
1. A VM job that finds every slot busy starts a VM at once, even when a slot frees a second later. The race "a VM boots for a job another VM already took" hit `deploy-site-dev` behind `site-image-dev`.
2. With `vmFirst` the VM runner carries the lane tags, so GitLab hands any pending lane job to any free VM slot, whatever the dispatcher decided. The warm VM ran lane jobs while Docker jobs started new VMs.
3. Four parallel lane claims raced past the M6.1 reservation onto two free slots.

## Terms

- **VM job:** a job that `pool_for` routes to a VM pool.
- **Lane job:** a job routed to a lane.
- **Live VM:** a VM of the pool that is not draining.
- **Typical duration** of a job name: the fold of its finished runs (`ledger::fold_duration`).

## Rules

R1. Config.
- A VM pool may set `maxQueueS`: seconds a VM job may wait for a paid slot before ciburst buys another VM. Whole number 0 to 3600, default 90 (about one VM boot). 0 restores the M6.1 behaviour: a VM job without a free slot starts a VM at once. On a lane it is a validation error.
- A lane's `vmFirst` (default true when the config has a VM pool) now means: its jobs may run on idle paid VM slots while the dispatcher allows spill (R6, R8).

R2. Queue first.
A pending VM job:
- **free slot:** claims it, as today;
- **no live VM** and no VM intent in the ledger window: takes the burst path, as today;
- **otherwise**, all live VMs are busy or starting: the dispatcher evaluates the start rule (R4) with this job as the newest queued job.
  - If the rule gives this job no VM, it records `Queued` (`Schedule::enqueue`) and answers `200 {"result":"queued","pool":"<vm>","etaS":<seconds or null>,"ms":...}`, log `info queued ... eta_s=...`.
  - If it gives this job a VM, the burst path runs as today.
  - At `maxRuns` live VMs the job is queued, never answered `at_capacity`.

R3. Job tracking.
Job events of VM jobs and lane jobs with status `running`:
- `Schedule::started(pool, Running { job, name, started })`. `started` comes from `build_started_at`, which GitLab writes as `2026-10-26 06:45:46 UTC`; it is now when that is missing.

Job events with status `success`, `failed`, `canceled` or `skipped`:
- `Schedule::finished(pool, job, name, duration)`, with `build_duration` rounded to whole seconds for `success` and `failed`, `None` otherwise.

Both answer `200 {"result":"tracked","status":"<status>","pool":"<pool>","ms":...}`. `created`, `waiting_for_resource` and other statuses stay `ignored`. The pool key is the VM pool's tag for VM jobs and the lane's tag for lane jobs.

R4. Start rule, per VM pool, at time `now`:
1. **Running jobs:** for each running VM job of the pool, `remaining = max(0, typical(name) - (now - started))`; with no typical duration, `remaining` is 0. Sort ascending.
2. **Queued jobs:** sort oldest first, by `at`, then job id.
3. **Starting VMs:** the free slots of VMs younger than 10 minutes in state `starting` take the oldest queued jobs first. Each such job expects its slot when the VM is up: `remaining` 0.
4. **The rest:** each further queued job, in order, is matched to the next running job and expects a slot after that job's `remaining`. A job left over expects no slot.
5. **Who needs a VM:** a queued job needs one when it expects no slot, or when `(now - at) + expected > maxQueueS`.
6. **How many to start:** `ceil(needing / slots)` VMs, at most `maxRuns` minus live VMs. Each starts with `taken` 0 and the labels `job=queue:<oldest needing job>` and `pipeline`. Log `info queue_started pool=... vms=... needing=...`.

Started VMs are not written to the ledger. To keep two evaluations at the same moment from starting twice, an evaluation that starts VMs first writes the marker `ciburst/intents/_queue/<pool>/.started` (plain PUT). It skips starting while that marker is younger than 15 s, comparing the object's `Last-Modified` or a time in its body. Residual race: at most one VM-hour.

R5. When the rule runs:
- on every pending event of a VM job without a free slot (R2);
- on every `/vm` report of a VM of the pool;
- on every pending lane job event for a lane whose VM pool has queued jobs.

Queued entries older than 30 minutes count as gone (a lost event) and are removed when read.

R6. Spill runner.
- **Runners:** a VM pool with at least one `vmFirst` lane gets a second GitLab runner, `<name>-<vm tag>-spill`. Its tags are the VM pool's tag plus each `vmFirst` lane's tag, in config order. The VM pool's own runner keeps only its own tag.
  - Plan lines: `create  gitlab runner <name>-<vm tag>-spill  (tags vm, node24)`, `update  gitlab runner <name>-<vm tag>  (set tags vm)`.
- **Outputs:** `CIBURST_SPILL_RUNNER_ID_<TAG>` and `CIBURST_SPILL_RUNNER_TOKEN_<TAG>` (secret, masked). `Secrets::spill_tokens` holds the token by VM pool tag.
- **Function:** the secret variable `RUNNER_SPILL_TOKEN_<TAG>`.
- **VM:** the start env gets `RUNNER_SPILL_TOKEN`. `destroy` and `rotate runner` cover the spill runner too.
- **VM agent:**
  - Every slot starts with `RUNNER_TOKEN`.
  - While the last report answer said `"spill": true`, every idle slot runs with `RUNNER_SPILL_TOKEN`; otherwise with `RUNNER_TOKEN`. A slot changes token only while idle: `SIGQUIT`, wait for its exit, start it with the other token. A busy slot changes once its job ends.
  - Reports carry `spill`: the slots currently running with the spill token.
  - Without `RUNNER_SPILL_TOKEN` a VM never spills.
- **Capacity:** the provider writes `spill` into the server's tags (`ciburst-spill:<n>`; Hetzner label `ciburst-spill`), and `VmCapacity::spill` reads it back.

R7. Report answer.
- **Shape:** `200 {"result":"reported","spill":<bool>,"nextReportS":<seconds>,"ms":...}` (`VmReportAnswer`).
- **`spill` is true** when all of these hold:
  - the VM's pool has a spill runner;
  - the pool has no queued VM job;
  - no open pipeline record lists a VM job of this pool without a seen marker;
  - the VM is not draining.
- **`nextReportS`:** 15 while `spill` is true or the pool has queued jobs, 30 while the VM is busy, 600 otherwise.
- **Agent side:** the agent reports on every change and at the latest after `nextReportS` of the last answer, clamped to 10 to 600 s; before its first answer, after 600 s.

R8. Lane jobs.
A pending lane job of a `vmFirst` lane, while R7 would answer `spill` true for its VM pool and a live VM of that pool reported `min(free, spill) > 0` within the last 30 s:
- It records `Queued` under the lane's tag and answers `200 {"result":"spilled","pool":"<lane>","vm":"<run id>","ms":...}`; no lane run starts.
- Every evaluation of R5 for the VM pool also starts a lane run for each queued job of its lanes that is older than 20 s (`SPILL_WAIT_S`) and still queued, below the lane's `maxRuns`. Log `info spill_fallback lane=... job=...`.
- Otherwise the lane job starts a lane run as today.
- The D47 claim of a VM slot for a lane job and the M6.1 reservation (its rule R6) are removed. The `seen` markers stay; R7 reads them.

R9. Without `Schedule` (`Dispatcher::with_schedule(None)`), the dispatcher behaves as in M6.1 with `vmFirst` false: no queueing, no spill. A `Schedule` error logs `warn schedule_failed op=...` and falls back the same way for that call; it never fails an answer.

R10. Docs:
- README: scheduling, `maxQueueS`, what `vmFirst` means now;
- `AGENTS.md`: `maxQueueS` in step 6 and lanes in step 7;
- RUNBOOK: the new answers, the queue keys, failure modes, and an M6.2 drill section;
