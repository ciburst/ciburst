# M6.3: one fleet, many projects

Go for the spec: owner, 2026-10-26 ("Plan B looks good", "we can assume vm sharing per default for now"). Spec D57 to D59. Base commit: named in each agent prompt.

## Goal

The first project sets ciburst up as today, with all its variables. Any later project, in any group or organization, joins that setup with one manual job and two variables, and never touches Scaleway. All projects share one dispatcher, one bucket, the VMs and the lanes, so one VM's paid hour serves every project.

## Terms

- **Fleet:** a deployment and the projects it serves.
- **Host:** the project that ran the first `ciburst-setup`; its CI variables hold the fleet's outputs.
- **Member:** a project that joined through `ciburst-join`. The host is the fleet's first member.

## Phase 0: measure before building

Gate for R5. On one VM, run `gitlab-runner run` with a `config.toml` that holds runners of two projects and `concurrent = 2`, then check:
- jobs of both projects run;
- never more than 2 jobs at once;
- an edited `config.toml` (a runner added, a runner removed) is picked up without a restart, and how long that takes;
- `SIGQUIT` drains gracefully;
- every job's `CI_PROJECT_DIR` and volumes stay apart.

Record the results in the runbook. If one fails, stop and report.

## Rules

R1. Fleet state in the bucket.
- The routing config and the member list move from the function's environment into `ciburst/fleet/config.json` and `ciburst/fleet/members/<project id>.json`.
- The dispatcher reads them, caching each for at most 30 s. A config or member change then takes effect within 30 s, with no function deploy.
- The function's environment keeps the secrets, the bucket location and the key that reads the fleet state.
- `ciburst-setup` writes the config object; it redeploys the function only when code or secrets change.

R2. Member records.
A member record holds:
- the project id;
- the webhook secret;
- the token of each runner the member registered (one per pool: VM pool and lanes);
- the join time.

The tokens are encrypted with a key from the dispatcher's secrets (AES-GCM; the key never leaves the function and the setup).

R3. Invite.
- `ciburst-invite`, a manual job in the host, reads the variable `CIBURST_INVITE` (a project id or path) and prints a join code. `ciburst invite <project>` does the same on the CLI.
- The join code holds:
  - the dispatcher URL;
  - the member's project id;
  - a webhook secret derived from the host's hook token and that project id (HMAC-SHA256);
  - an expiry, 7 days.
- The code is the only authorisation a member needs.

R4. Join and leave.
- The component input `role: member` (default `host`) replaces the setup, check and destroy jobs with `ciburst-join` and `ciburst-leave`. The member keeps `default: tags` and `.ciburst-docker`.
- `ciburst-join` reads `CIBURST_JOIN` (the code) and `CIBURST_GITLAB_TOKEN` (`api` and `create_runner` on the member project only), then:
  1. registers one runner per fleet pool in the member project, with the fleet's tags;
  2. creates the member's webhook (job and pipeline events, the derived secret);
  3. posts the runner tokens to the dispatcher's `/join`, authenticated by the code.
  It finishes within about 1 minute and logs `joined fleet <name>`.
- `ciburst-leave` deletes the member's runners and webhook and posts `/leave`.
- Joining twice replaces the earlier record.

R5. VMs serve every member.
- The VM agent runs one `gitlab-runner run` with one `[[runners]]` entry per member runner of its pool, and `concurrent = slots`. It takes over the work of today's per-slot `run-single` processes: busy detection, drain, report.
- The agent fetches the member runners from the report answer and rewrites `config.toml` when they change.
- Lane runs start with the lane runner token of the job's own project.

R6. Dispatcher across members.
- A job or pipeline event is accepted when its project is a member and its `X-Gitlab-Token` equals that member's webhook secret.
- Queue, warm start, records and the burst ledger work across members unchanged.
- `ignoreJobs` and the lanes are fleet-wide.

R7. Tools across members.
- `ciburst check` and the host's `ciburst-check` check every member.
- `ciburst status` lists the members, and the deliveries of each member's webhook.
- `ciburst-destroy` in the host refuses while members other than the host exist, naming them.

R8. Trust.
- VM jobs of all members share VMs (owner's default).
- The docs state that members can reach each other's job data on a shared VM, and that untrusted projects belong in separate fleets.

R9. Migration.
- Existing deployments become fleets with the host as the only member on their next `ciburst-setup`, with no change for their pipelines.
- The host's `gitlab.projectIds` beyond the first are migrated into member records whose runners are the host's runners enabled in those projects. A later `ciburst-join` there replaces them.

## Definition of done

`cargo fmt --check`, `clippy -D warnings`, `cargo test` (Windows and `scripts/test-linux.sh`), `cargo deny`, shellcheck, check-pins and the bootstrap test are green.

Fake-based tests cover each rule, among them:
- an expired or forged join code is refused;
- a member's events with another member's secret are refused;
- a config change takes effect without a deploy;
- the agent rewrites `config.toml` on a member change.

Live:
- the demo is the host; a second project in another namespace joins with one job and two variables;
- a pipeline of each project runs on the same VM;
- a config change applies within 30 s;
- the member leaves cleanly.

No identifying data, no em or en dash.
